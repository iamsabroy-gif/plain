# Developer guide

For people who want to change Plain: fix a bug, add a built-in, a library part or a practice
problem, improve the visualizer or the playground. If you only want to *use* Plain, start
at the [README](../README.md).

## Principles

These decide most questions about what a change should look like.

1. **No dependencies.** One C++17 compiler is the whole toolchain. Everything is header-only
   under `src/`; `main.cpp` includes the rest.
2. **One way to write each thing, and no new syntax for new features.** The language is
   deliberately small. Data structures, practice problems and tools are *libraries and commands*,
   never new keywords. `plain format` rewrites old spellings into the standard one.
3. **Errors teach.** Every error says what happened, on which line (with the line shown), and
   what to try. A new error message without a "what to try" is unfinished.
4. **The library explains itself.** Data structures are written in Plain in `lib/`, so a learner
   can read how a queue is built (`plain lib queue`). Prefer Plain over a hidden C++ built-in
   unless speed or access to the machine demands C++.
5. **Watching costs nothing when it is off.** Counting, tracing and practice use a second copy of
   the VM loop; a normal run compiles none of the hooks in.
6. **Learner-first output.** Teaching tools show the learner's own code and values, with no
   drawing code or annotations required of them.

## Quick start

```
make                 # build ./build/plain
make test            # run everything (see Tests); takes about a minute
./build/plain examples/tour.plain
./build/plain --explain -e "say 1 + 2"      # tokens, then bytecode, then run
```

`make` regenerates `src/libfiles.hpp` when anything in `lib/` changes (`sh tools/embed.sh`).
Without `make` (for example `install.sh --build`) the checked-in `src/libfiles.hpp` is used.

Useful while working:

| Command | Use |
|---|---|
| `plain --explain file.plain` | see the bytecode your change produces |
| `plain visualize file.plain` | step through a run in a page |
| `plain count file.plain` | comparisons, swaps, calls, instructions |
| `plain format --print file.plain` | see the standard style |
| `plain practice --selftest` | check every practice problem against its reference |
| `make pdf` (or `node tools/make-pdf.js`) | rebuild `docs/pdf/*.pdf` from the Markdown (needs Playwright's Chromium); fails on a broken link |
| `sh tests/bless.sh name` | re-save `tests/cases/name.expected` after you have read the diff |

## How it works

1. **Tokens** (`lexer.hpp`). Words, numbers, text and symbols. Keywords are matched
   case-insensitively and stored lower-case. `note:` lines and `#` comments are dropped (the
   formatter splits comments off itself). Each token records where it sits in the source.
2. **Bytecode** (`compiler.hpp`). A single-pass compiler: no syntax tree. Statements and
   expressions emit 32-bit instructions (8-bit operation, 24-bit operand; a few "wide"
   operations take a second word). Variables become numbered slots at compile time.
   `Program` holds everything that outlives one compile: global slots and values, compiled
   functions, source files loaded with `use`.
3. **Virtual machine** (`vm.hpp`). A stack machine. Integers and floats are stored inline in a
   16-byte `Value`; everything else (text, lists, maps, big numbers, decimals, objects) is
   reference counted, and `tasks.hpp` has the cycle collector for what counting can't free.
4. **Watching** (`observe.hpp`). `VM::executeT<OBS>` is the main loop compiled twice.
   `executeT<false>` is the normal run and contains none of the hooks; `executeT<true>` calls
   the Observer from every instruction and from calls, comparisons, list reads and writes,
   `say`, and errors. `VM::execute` picks one by whether `vm.obs` is set.
   Nested calls from built-ins (`map_each`, ...) go through `execute` too, so they are counted.

### Scope rules (and why the compiler looks the way it does)

* At the top level, `set` makes a **global**. Inside an action, `set` changes a variable of the
  action around it, or a global the top-level code already made, otherwise it makes a local.
  Actions at the top level are registered when compiled, so they can be called from above.
* A closure captures variables as **upvalues**: they point into the stack while the action is
  running, and are moved into the closure when the action returns (`closeUps`).
* **Loops and closures.** Each round of a `for` / `for each` loop must give closures its own copy
  of the loop variable. When the compiler sees `action` or `define` inside a loop body
  (`bodyHasClosure`), it gives the loop variable a slot of its own (`scopeLoopVar`; at the top
  level this makes a *local* of the main function) and emits `OP_FRESH` at the end of each round
  to close the upvalues of that range of slots (`VM::closeRange`). Loops without closures pay
  nothing.

### Errors

`fail(message)` throws `PlainError` (message, line, file). The VM fills in the line from the
bytecode when it unwinds, `try` / `on error` catches it, and `report()` in `main.cpp` prints it
with the source line. `PlainError::fatal` marks an error that `try` must not catch (the
instruction budget being used up).

### Modules and files

`use "name"` looks for a file next to the program, then packages in `plain_modules/`, then
`~/.plain/modules`, then the built-in library. Built-in library files have paths like
`<lib>/stack.plain` and live in `LIB_FILES` (see `modules.hpp`: `libSource`, `packedFile`).
`plain build` copies the interpreter plus every source it used onto one file; at start-up the
interpreter looks for that payload on itself.

## Recipes

### Add a built-in action (C++)

In `builtins.hpp`:

```cpp
BUILTIN(b_double_it) {                      // a[0..n-1] are the values, n their count
    needNumber("double_it", a, 0);          // helpers: argInt, argStr, argList, argMap, needArgs
    return numMul(a[0], Value::integer(2)); // return Value() for "nothing"
}
// ...and add   {"double_it", 1, b_double_it},   to the table in registerBuiltins()
// (arity -1 means "any number of values": check with needArgs)
```

Then: say what to try in every `fail(...)`; add the name to the table in
`docs/LANGUAGE.md`; add a case to `tests/cases/` and bless it; if it needs threads, sockets or
processes, make the web build refuse it (see `PLAIN_POSIX` in `builtins.hpp`). If it is easy to
write in Plain, put it in the `PRELUDE` string in the same file instead.

### Add a library part (Plain)

1. Write `lib/yourthing.plain`: a comment block saying *how it works* with a tiny usage example,
   then a class. Keep it readable; a learner is the audience. Follow the existing files.
2. Add `use "yourthing"` to `lib/dsa.plain`, and a line to the `about` table in `libCommand()`
   (`main.cpp`) so `plain lib` lists it.
3. `sh tools/embed.sh` (or `make`), then `plain format lib/yourthing.plain`.
4. Add a case to `tests/cases/` (`dsa_*.plain`) that checks it against a brute-force model on
   pseudo-random operations, not just two hand-written examples. `tests/cases/dsa_advanced.plain`
   shows the pattern.
5. Add a row to the table in `docs/LEARNING.md`.
6. If objects of your class should look special in the visualizer, see
   [the player](#add-a-view-to-the-visualizer).

Nodes of trees, chains and graphs should be plain maps (`{value: ..., left: ..., right: ...}`):
the visualizer draws those automatically. A tiny module looks like this:

```plain
class Box
    init with thing
        set me's thing to thing
    end

    define show_it
        say "A box holding", me's thing
    end
end

new Box("a kite")'s show_it()
```

```output
A box holding a kite
```

### Add a practice problem

Create `lib/problems/your-id.plain`. The file name is the id. It has three parts: a map called
`__problem`, optional helper actions whose names start with `__`, and a reference solution called
`__reference` between two marker lines. Use an existing file as the template; the rules are:

* Keys: `order` (number; decides the listing order), `title`, `topic`, `level` (1 to 3),
  **`function`** (the action learners write; **not** `action`, which is a reserved word and can't
  be a map key), `params` (text, like `"numbers, target"`), `statement`, `examples` (shown),
  `hidden` (checked, never shown), `hints` (at least 2, easiest first), `complexity`,
  `explanation`, and `mode: "changes"` if the learner changes the first value in place instead
  of giving something back.
* Each test is `{args: [...], expect: ..., note: "..."}`. `note` is shown when a hidden test
  fails, so write what it *checks* ("an empty list"), never the data.
* At least 1 example and 4 hidden tests. Include edge cases, and one **big** test when the
  point of the problem is the faster idea: a naive solution is stopped after 120 million
  instructions with "ran far too long".
* **Expected values must not come from your own reference solution.** Use hand-worked results,
  known values (Fibonacci, N queens counts), or a *different* algorithm (see the oracle helpers
  in `generate-parentheses.plain` and `hot-potato.plain`). The self-test passing is meaningless
  if the expectation was copied from the code it tests.
* The solution goes between `# --- solution ---` and `# --- end solution ---`. Its text is shown to
  learners with `__reference` renamed to their action, so make it read well. Helper actions that
  belong to the solution go inside the markers.
* Remember `range` and `slice` include both ends.

Then `plain format lib/problems/your-id.plain`, `sh tools/embed.sh`, and
`plain practice --selftest`. Optionally add a naive solution to `tests/practice_test.sh` to prove
the big test does its job.

### Add or change a lesson

Lessons are text files in `lib/lessons` (`NN-name.lesson`); the format is described at the top
of `src/lessons.hpp`. Each exercise needs a task, the `output` the program must say, at least one
`hint` and a `solution`; `input` (typed in for `ask`), `uses` and `avoid` (words, `{}` for a
text template, `[]` for a list) are optional. Write `\{` for a brace in text that is not a
template. Then `sh tools/embed.sh` and `plain lesson --selftest`, which runs every solution
and checks that no empty starter passes. The playground reads the same lessons through
`plain lesson --json`, so there is nothing else to update.

### Add a command

Commands live in `tools.hpp` (or `practice.hpp`) as `static int nameCommand(const std::vector<std::string>& args)`.
Dispatch it in `main()` (`if (cmd == "name") return nameCommand(args);`) and add it to `usage()`.
Conventions: take a file *or* `-e SOURCE`; exit 0 on success, 1 for a problem with the
learner's program, 2 for a usage mistake; print plain-English errors. If a browser needs it, give
it a machine-readable mode (`visualize --json -e ...` is the example).

To observe a run:

```cpp
auto run = std::make_unique<WatchedRun>();   // a Program and an Observer
setUp(run->prog);
VM vm(run->prog);
run->ob.maxInstr = 100000000;                // stop runaway programs (a fatal error, not catchable)
vm.obs = &run->ob;                           // setting this selects the watched loop
Compiler compiler(run->prog, src, file);
vm.run(compiler.compileMain());
// run->ob.compares, .swaps, .writes, .calls, .instr, .callsByName
```

### Add a view to the visualizer

`lib/viz/player.html` is one file of plain HTML, CSS and JavaScript with no libraries. The data is
the JSON trace below, embedded in place of `/*__PLAIN_DATA__*/null`. You can develop it without
rebuilding anything: run `plain visualize prog.plain -o /tmp/p.html` and open that file.

* `render(value, ctx)` decides how a value is drawn. Detection is by *shape*: a list of numbers is
  bars; a map or object with `value` and `left`/`right` is a tree; `value` and `next`, a chain;
  `value` and a `children` list, a general tree; a map of lists whose items are its own keys, a
  graph. Add your shape to `render`, or special-case a library class in `renderRecord`
  (the way `Queue`, `Stack`, `Heap`, `Deque` and `RingBuffer` are).
* `ctx.step` holds the highlights of the current step (`c` compared, `w` written, `s` swapped,
  all as `[listId, index]`), `ctx.labels` maps object ids to the names of variables that point at
  them, and `ctx.scope` has the scalar variables of the frame (used for index markers).
* Keep it working in light and dark mode and at phone width, and keep colour from being the only
  signal (compared and moved items also differ in pattern).
* `node tests/web_e2e.js` exercises the page in a real browser if Playwright is installed.

## The trace format

`plain visualize` records the run; `Observer::traceJson` writes it. Top level:

| Key | Meaning |
|---|---|
| `sources` | `[{name, text}]`: the source files shown |
| `files` | file names; a step's `fi` indexes into this |
| `watch` | names from a `# watch: a, b` comment (empty: show everything) |
| `vals` | interned values; everything else refers to them by index |
| `out` | what the program said, one string per `say` |
| `calls` | the call tree: `{p: parent or -1, s: first step, e: step it returned at or -1, r: value index of the answer, n: name, a: [value indexes of the arguments]}` |
| `steps` | one per line that ran, see below |
| `counts` | `{instructions, comparisons, swaps, writes, calls}` for the whole run |
| `truncated` | the recording stopped at `maxSteps` (default 6000) |
| `error` | `null` or `{msg, line}` |

A step: `l` line, `fi` file index, `d` call depth, `o` how many `out` chunks exist so far, `cs` call
node, `g` global variables `[[name, valueIndex]]`, `f` frames `[{n, l, v: [[name, valueIndex]]}]`
(outermost first), and optionally `r` (value index of what the action returned), `c` / `w` / `s`
(compared / written / swapped items) and `e` (an error message). The state in a step is *after*
that line ran, which is why the player says "the highlighted line has just run".

A value is JSON: `null` (nothing), booleans, numbers, strings, `{"$":"n","s":"..."}` for big
integers, decimals and non-finite floats, `{"L":id,"n":count,"v":[...]}` for a list,
`{"M":id,"n":count,"v":[[key,value]...]}` for a map, `{"O":id,"c":"Class","n":..,"v":[[field,value]...]}`
for an object, `{"C":name}` / `{"F":name}` for a class or action, and `{"$":"more"|"deep"|"cycle"}`
where the recorder cut it off. `id` is stable for the life of the object, so highlights and
pointers can refer to it. Lists show at most 80 items, maps 60, a variable at most about 600
values. Steps inside the built-in library are folded into the line that called them
(`--into-library` records them).

## The documentation site

The **Documentation** tab of the published site is made by `node tools/build-docs.js [folder]`
(`make docs-site` builds it into `web/docs`, which git ignores; open `web/docs/index.html`). The
Pages workflow builds it into `site/docs` on every change to `main`, so it is never edited by hand:

* one page per guide in `docs/` (and the README as "Getting started"), converted by
  `tools/markdown.js`, the same converter the PDFs use;
* pages made from the sources: the lessons (`plain lesson --json`), the practice problems
  (`plain practice --json`, which leaves out hidden tests, hints and solutions) and the library
  reference (the first comment block of each `lib/*.plain`);
* a sidebar in four groups (for children, learning to program, building with Plain, working on
  Plain), search over every section (`search-index.js`), an "On this page" list, and a "Try it"
  button on every ` ```plain ` example, which opens it in the playground (`../#c=...`);
  `../#lesson=3` opens a lesson in the playground.

A new guide goes into `GUIDES` and `NAV` at the top of `tools/build-docs.js` (and into `DOCS` in
`tools/make-pdf.js` for the PDF). The build stops with an error on a link that leads nowhere;
`tests/docs_site_test.js` checks the site in a browser.

## The browser playground

`web/` is a static site: `index.html` (editor, Run, Watch it run, Count the work, examples, share
links), `worker.js` (runs the interpreter in a Web Worker so a stuck program can be stopped, and
supplies the small "operating system" the interpreter needs), `syntax.js` and `plain.wasm`.
"Watch it run" runs `plain visualize --json -e ...` in the worker and gives the trace to the same
player that `plain visualize` writes.

**The editor** is a transparent `<textarea>` over a coloured copy of its text (same font, padding
and scrolling, so the two line up exactly; the test checks the copy's text equals the editor's).
`syntax.js` is the one place that knows how Plain looks: it colours code (`PlainSyntax.highlight`,
used by the playground, the docs site and the PDFs, so they agree) and counts blocks
(`opensBlock`, `unclosedBlocks`, `matchingIndent`). Both are word-based, not a parse, so they are
quick enough for every key press. On top of it the editor:

* indents after a block line, and when Enter is pressed at the end of one whose block is not
  closed anywhere, adds the `end` and leaves the cursor inside (`unclosedBlocks(text) > 0`);
* moves `end`, `otherwise` and `on error` back to the line that opened their block as the last
  letter is typed (`matchingIndent`);
* runs `plain check --json -` (the program on standard input; one line of JSON back) in a second
  worker 600 ms after typing stops, and underlines the line it names: red for a mistake, orange
  (`incomplete`) for a block that is still open. The VS Code extension does the same
  (`plain.checkAsYouType`). It finds what the compiler finds; a name that was never set is only
  noticed when the program runs.

A new keyword needs adding to `syntax.js` (colours), `editors/vscode/syntaxes` (the same, for
VS Code) and, if it opens a block, `opensBlock` (and `flowchart.js`, if it should be drawn as
more than a box).

**The flowchart** (`flowchart.js`) reads a program line by line, like `syntax.js`, into ifs,
loops, `try`, steps and jumps (`give back`, `stop`, `skip`, `fail`), with each `define` and each
class action as a chart of its own, and lays it out as a structured flowchart in SVG. Every box
knows its lines, so `boxForLine` finds the box for a step of a "Watch it run" trace: the player
posts `{plainPlayerAt, line, file}` to the page as it moves, and the page lights that box and
counts the steps per box; a click on a box posts `{plainPlayer: "line", lines}` back, and the
player goes to the next step on one of those lines. `tests/flowchart_test.js` draws every
program in the repository and checks that every line has a box and that no boxes overlap.

**The algorithm gallery** is `algorithms.js`: one entry per algorithm (name, picture, group,
cost, a sentence, and the program). A new one needs an expected answer in
`tests/algorithms_test.js`, which also checks it is in the standard style, records in full
(keep inputs small: the player records 6,000 steps) and that every step lands on a box.

The interpreter is this same source built with `-DPLAIN_WASM` (set automatically by a WASI
compiler). `value.hpp` defines `PLAIN_POSIX` for full builds (not Windows, not WebAssembly):
sockets, processes, git and threads sit behind it, and the web build refuses those features with
a clear message. Add new machine-dependent code behind the same macro.

Building `plain.wasm` needs the [WASI SDK](https://github.com/WebAssembly/wasi-sdk/releases)
(34 or newer, which has the exception-enabled C++ libraries):

```
WASI_SDK=/path/to/wasi-sdk sh tools/build-wasm.sh
node tests/wasm_test.js            # runs worker.js against plain.wasm in Node
node tests/web_e2e.js              # real browser, needs Playwright
cd web && python3 -m http.server   # open http://localhost:8000 (workers need http, not file:)
```

Notes that cost time to find out:

* The build uses WebAssembly's *new* exception encoding (`-mllvm -wasm-use-legacy-eh=false`, with
  `-lunwind`), matching the SDK's own libraries. A module that mixes old and new is rejected by
  Chrome even though Node accepts it. It needs Chrome or Edge 137+, Firefox 131+, Safari 18.4+.
* The worker batches its output (every 30 ms) and the page stops a program that says more than
  300,000 letters; without that, a loop that prints constantly freezes the page.
* `poll_oneoff` (used by `wait`) is a busy wait, because a worker without cross-origin isolation
  can't sleep with `Atomics.wait`.
* `.github/workflows/pages.yml` builds and publishes `web/` whenever `main` changes. One-time:
  Settings, Pages, Source: "GitHub Actions".
* To host it on [Render](https://render.com) instead (or as well): `render.yaml` is a Blueprint for
  a free static site. On Render: New, Blueprint, pick the repository. Its build runs
  `sh tools/render-build.sh`, which does what `pages.yml` does and leaves the site in `site/`;
  run it locally to try the same build.

## Tests

`make test` runs all of these. Each is a shell (or Node) script in `tests/`.

| Script | What it checks |
|---|---|
| `run_tests.sh` | every program in `tests/cases/` prints what its `.expected` file says (language, errors, library) |
| `pkg_test.sh` | the package manager |
| `format_test.sh` | `plain format` rewrites old spellings, is idempotent, never changes a program's output; `lib/` is in the standard style |
| `lib_test.sh` | `src/libfiles.hpp` matches `lib/`; `plain lib` and `--copy` work |
| `viz_test.sh` | `visualize` writes one standalone page; `count`; `growth` finds the right curves; `compare` |
| `practice_test.sh` | all problems pass their self-test; the learner flow; naive solutions are stopped |
| `webmode_test.sh` | the `-DPLAIN_WASM` variant, built natively, behaves like the normal one |
| `wasm_test.js` | `worker.js` + `plain.wasm` in Node (skipped if not built) |
| `web_e2e.js` | the real playground in Chromium (skipped without Playwright and `plain.wasm`) |
| `docs_test.sh` | the programs in `docs/KIDS.md` and this file run and print what the page says |

Writing a test case: put `name.plain` (and `name.in` for typed input, `name.expected`) in
`tests/cases/`, run `sh tests/bless.sh name`, **read** the result, and commit it. A test case
shows output *and* error messages, since the error wording is part of the product.

The programs in the documentation are tested too (`tests/docs_check.py`): a fenced block marked
`plain` is run and the next block marked `output` must match; `plain-fails` expects an error;
`input` supplies typed answers; `plain-nocheck` is not run.

## Releasing

`install.sh` (Mac and Linux) and `install.ps1` (Windows) download ready-made programs from the
latest GitHub release, so users need no compiler. `.github/workflows/release.yml` builds them
for Linux x86_64 and arm64, macOS Intel and Apple Silicon, and Windows (MinGW, static) when a tag
is pushed:

```
git tag -a v2.3.0 -m "Plain 2.3.0" && git push origin v2.3.0
```

Afterwards: check the Actions tab, then run both installers on a clean machine. The Windows build
has had the least testing. Linux files are built on an older glibc and need glibc (not Alpine).
The version string is `VERSION` in `main.cpp`.

## Gotchas

Things that have already bitten people (and the library files):

* **Reserved words can't be names**, including variables, parameters, class names, method names
  and map-literal keys. The common traps: `at`, `most`, `least`, `item`, `times`, `length`, `to`,
  `from`, `by`, `of`, `in`, `end`, `back`, `each`, `add`, `remove`, `set`, `action`, `new`, `me`,
  `parent`. After `'s`, any word is fine (`p's item`). The error names the word and suggests
  another; use that. `Set` is a keyword too (any case), hence `Unique`.
* **Lists count from 1.** `slice(x, a, b)` and `range(a, b)` include both ends. `x[0]` is an error.
* **Map keys** must be text, numbers or true/false.
* `sort` can't compare lists with each other; use `sort_by(items, action with p gives p[1])`
  (it is stable). `%` is never negative for a positive divisor; `quotient` rounds down.
* A line that is only an expression must be a call (or Plain says it works out a value and does
  nothing with it).
* `end` closes every block; a method can't be called `add`, `remove` or `contains`.
* `set` inside a *top-level* loop body creates globals, so closures there share them; put the loop
  in an action for one variable per round.
* The formatter indents the inside of brackets one level; keep data lists in `lib/` in that style
  (`plain format` will do it).
* In `.plain` files under `lib/`, the first comment block is documentation for learners. Keep it
  true when you change the code.
* **Text is never changed in place** (C++ side). `Str` remembers its hash, so code that edits
  `asStr(v)` of a value that may already be a map key would break lookups: make a new string.
* **Changing a class bumps `g_classVersion`.** Each `obj's action(...)` call site caches the method
  it found for a class; anything new that adds or replaces methods (or a parent) must bump it.
* Maps of up to `Map::SMALL` entries have no hash index (they are searched in order); always go
  through `find` / `set` / `remove`, never `index` directly.
* A line like `sort(xs)` that throws away a built-in's answer is a compile error; the lists of
  such built-ins are in `Compiler::checkDiscarded`. Add new answer-only built-ins there.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| `make` says `No rule to make target lib/problems/*.plain` | an old Makefile; it must use `$(wildcard ...)` |
| `src/libfiles.hpp is out of date` (lib_test) | run `sh tools/embed.sh` and commit the result |
| `'x' is a reserved word` inside a library file | rename the variable (see Gotchas) |
| `wasm-ld: undefined symbol: __cpp_exception` | the WASM build is missing `-lunwind` |
| `module uses a mix of legacy and new exception handling instructions` | build with `-mllvm -wasm-use-legacy-eh=false` |
| the playground says "Could not start" | opened from `file:`; serve it over http |
| `make test` fails only in `web e2e` | Playwright/Chromium missing or `plain.wasm` is stale: rebuild it |
| a problem passes `--selftest` but a correct solution fails | the expected value was copied from the reference; recompute independently |

## Limits

* Tasks run one at a time (like Python's global lock: they overlap while waiting for files or
  the network, not on several cores). Nothing runs in parallel.
* Decimals do not mix with floats, and have no `sqrt` / `sin`; use `float(x)`.
* `plain build` copies the interpreter plus your source: the result is standalone but contains
  the interpreter, not machine code made from your program.
* `https` uses OpenSSL, loaded with `dlopen` when first needed (`src/tls.hpp`), so a ready-made `plain` still starts without it; then `https` falls back to the `curl` program. Windows has no networking or `plain install` yet. The web
  playground has neither, nor tasks nor files.
* `plain visualize` records at most 6,000 steps, shows at most 80 items of a list and about 600
  values per variable. Counts do not include the inside of `sort()` and other built-ins.
* `Unique` and graph node names must be text, numbers or true/false (map keys).
* macOS and Windows builds come from the same portable code but have been tested less than Linux.
